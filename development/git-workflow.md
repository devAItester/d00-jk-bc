# Git workflow

При разработке важно различать **commit**, **branch** и **tag**. Они решают разные задачи.

## Commit

**Commit — зафиксированное состояние проекта.**

Это точка, к которой можно вернуться и с которой можно сравнивать дальнейшие изменения.

Рабочее правило:

> Получился осмысленный результат — сделай commit.

Не надо ждать завершения всего проекта. Коммиты должны фиксировать небольшие законченные изменения.

## Branch

**Branch — отдельная линия разработки.**

Ветка нужна не для того, чтобы «сохранить точку», а чтобы независимо развивать идею, не ломая стабильное состояние.

Для эксперимента:

```sh
git switch main
git pull
git switch -c experiment/structure
```

Дальше работа идёт в этой ветке:

```sh
git add .
git commit -m "..."
git push -u origin experiment/structure
```

Если эксперимент оказался правильным, его изменения можно объединить с `main`.

Git описывает branch как линию разработки; новая ветка может начинаться с конкретного commit или tag.

[Git — git-branch documentation](https://git-scm.com/docs/git-branch)

## Tag

**Tag — имя для конкретной точки истории.**

Поэтому для нашего случая tag лучше ветки подходит для фиксации вехи:

```sh
git tag -a p0 -m "clean visual baseline"
git push origin p0
```

После этого `p0` продолжает указывать именно на достигнутое состояние, даже если `main` пойдёт дальше.

Git прямо описывает tag как ссылку на определённую точку истории; аннотированные tags предназначены для таких именованных состояний.

[Git — git-tag documentation](https://git-scm.com/docs/git-tag)

## Наш рабочий цикл

Для этого проекта используем простую схему:

```text
main
  │
  ├── стабильная последняя точка
  │
  └── experiment/...
          │
          ├── commit
          ├── commit
          ├── commit
          │
          └── результат принят
                    │
                    ▼
                  main
                    │
                    └── tag p1
```

То есть:

1. `main` содержит последнее принятое состояние.
2. Новую идею начинаем в отдельной `experiment/...` ветке.
3. Каждый законченный шаг фиксируем commit.
4. Проверяем результат.
5. Если результат принят — объединяем ветку с `main`.
6. На важной вехе ставим tag.
7. Следующий эксперимент начинается уже от нового `main`.

### Почему не надо создавать branch для каждой точки

Ветка отвечает на вопрос:

> **«Где я сейчас развиваю эту идею?»**

Tag отвечает на вопрос:

> **«Где была достигнута эта конкретная точка?»**

Поэтому после принятия эксперимента ветку можно удалить, а tag останется постоянной отметкой.

Чистый визуальный baseline нового проекта зафиксирован commit:

```text
89d46f2  Create clean visual baseline
```

От него начата ветка:

```text
experiment/structure
```

Это и есть первый эксперимент: спроектировать структуру нового сайта с нуля, сохраняя текущий визуальный результат как reference.

## Источник истины

Для экспериментов важно не путать Git с резервной копией.

- **commit** — состояние проекта;
- **branch** — линия разработки;
- **tag** — именованная веха;
- **main** — принятый результат;
- **experiment/** — работа над новой идеей.

Так история проекта показывает не только конечный код, но и последовательность принятых архитектурных решений.
