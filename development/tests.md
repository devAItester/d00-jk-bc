# Tests

Эта статья описывает проверки, которые должны выполняться после изменения исходников. Цель — не просто получить успешный Jekyll build, а проверить свойства опубликованного HTML, из-за нарушения которых визуально исчезают пункты.

## 1. Почему одного build недостаточно

Успешная сборка доказывает, что Jekyll смог обработать шаблоны и создать `_site`. Она не доказывает, что каждый ожидаемый узел действительно попал в конкретный список.

Для регресса «пропуск в списке» нужны два уровня:

    исходники
        ↓
    проверка front matter
        ↓
    jekyll build
        ↓
    проверка сгенерированного HTML
        ↓
    deploy
        ↓
    проверка production

## 2. Защита front matter

`scripts/check-pages.sh` проверяет каждый Markdown-файл, который является частью исходного дерева, и требует непустой `title`.

Это важно для навигации: `nav.html` и списки используют `p.title`. Пустой title может превратить страницу в пустой или отсутствующий визуальный пункт.

Проверка должна выполняться до `jekyll build`.

## 3. Регрессионный тест главного списка

Главная страница содержит список узлов из `site.pages`.

Критическое правило:

    root index.html
        не является элементом списка

    любой другой публичный Markdown-узел
        с непустым title
        должен быть представлен в списке

Особенно нельзя исключать все `*/index.md`.

`section/index.md` — это публичная страница раздела, а не технический файл, который можно безусловно удалить из списка.

Тест `scripts/check-site.sh` выполняется после сборки. Он:

    1. открывает `_site/index.html`;
    2. находит первый `<ul>` внутри `<main>`;
    3. собирает его ссылки;
    4. строит ожидаемый набор из Markdown-файлов с непустым `title`;
    5. исключает только корневой `index.md`;
    6. сравнивает фактический и ожидаемый набор;
    7. завершает CI с ошибкой при любом пропуске или лишней ссылке.

Таким образом, исправление нельзя случайно вернуть в шаблон без падения CI.

## 4. Что было сломано

Старая логика главной страницы содержала условие:

    unless p.path contains '/index.md'

Оно исключало не только технический корневой файл, но и страницы разделов:

    audio/index.md
    development/index.md
    reference/index.md
    ...

Это было неверно: эти файлы являются узлами дерева и имеют собственные URL и `title`.

Правильное условие — исключить только саму корневую страницу. Сейчас список строится так:

    p.path != 'index.html'
    p.title != ''

а URL берётся из:

    p.url | relative_url

Это одновременно устраняет регресс пропуска и не дублирует логику построения URL.

## 5. Проверка навигации

Для `nav.html` отдельно проверяются:

    /
    /section/
    /section/page/
    глубокий узел

На глубине 2+ ожидаются локальные группы:

    children(grandparent)
    children(parent)
    children(current)

Проверяется:

    - нет пустых <ul>;
    - нет вложенных <ul> внутри navigation;
    - текущая страница получает class="self";
    - непосредственный родитель получает class="parent";
    - ссылки используют relative_url;
    - глубина дерева не ограничена.

Для глубокого теста используется дерево минимум из 60 уровней.

## 6. Проверка whitespace

Референс использует:

    nav ul li {
      white-space: pre;
    }

Поэтому переносы и отступы исходного HTML внутри `<li>` становятся визуально значимыми.

Элементы меню должны генерироваться без текстовых переносов вокруг ссылки:

    <li><a ...>...</a></li>

Это отдельный регрессионный тест визуального соответствия референсу: успешный HTML может быть семантически допустимым, но иметь неправильные вертикальные интервалы.

## 7. Тест порядка меню

Порядок должен проверяться не только наличием всех ссылок, но и их последовательностью.

В текущем дереве `development/_menu` задаёт:

    tests.md
    navigation.md

а остальные страницы каталога должны следовать после них в алфавитном порядке:

    tests.md
    navigation.md
    path-and-url.md
    svg-identity.md

Проверка должна также подтверждать два отрицательных случая:

    неизвестное имя в _menu
        → ошибка сборки

    повторное имя в _menu
        → ошибка сборки

При отсутствии `_menu` порядок должен быть обычным алфавитным.

## 8. Порядок CI

Workflow должен выполнять проверки в таком порядке:

    checkout
        ↓
    scripts/check-pages.sh
        ↓
    jekyll build
        ↓
    scripts/check-site.sh _site /flatfiletxtdb
        ↓
    upload-pages-artifact
        ↓
    deploy-pages

Если source-level или generated-HTML test не проходит, deployment не должен происходить.

## 9. Production

После успешного deployment проверяется именно опубликованный сайт:

    https://devaitester.github.io/flatfiletxtdb/

Минимальный набор:

    /
    /development/index.html
    /development/navigation.html
    /development/tests.html

На главной нужно проверить не только наличие списка, но и наличие всех узлов, включая страницы-разделы.

Production считается проверенным только после проверки опубликованного HTML, а не после сообщения `jekyll build` или успешного commit.

## Итог

Проверка «пропуск в списке» теперь состоит из двух независимых гарантий:

    source
        title существует
        ↓
    build
        HTML создан
        ↓
    generated HTML
        все ожидаемые страницы представлены
        ↓
    production
        опубликованный результат совпадает с проверенным build

Это минимальная защита от повторения именно того класса ошибки, который уже возникал на сайте.
